## 一、文档说明

### 1.1 文档目的

本文档为"麦乐迪零食购物商场系统"的需求规格说明书（SRS），依据 IEEE Std 830-1998 规范结构编写。其目的在于：

1. 明确系统功能边界，作为开发、测试、验收的统一依据；
2. 作为毕业设计论文的"需求分析"章节原始材料；
3. 在答辩评审时，可作为"需求阶段交付物"佐证项目完整度。

### 1.2 适用范围

本文档适用于本项目的全部功能模块，包括前台用户端、后台管理端、推荐系统、数据大屏四大子系统。

### 1.3 术语约定

- **"系统" / "本系统"**：指"麦乐迪零食购物商场系统"。
- **"用户"**：泛指前台消费者，包含游客、普通用户、会员用户三种状态。
- **"管理员"**：泛指后台管理人员，包含超级管理员与运营管理员两种角色。
- **"会员用户"**：原 V1.0 中部分位置使用的 "VIP" 角色名称，本版本统一为 "**会员用户**"。"VIP" 仅作为代码层枚举值（如 Spring Security `GrantedAuthority` 字符串）保留，不在文档正文中使用。

## 二、项目概述

### 2.1 项目背景

**市场背景**：零食赛道是中国电商增速最快的垂直品类之一，2024 年市场规模超 1.5 万亿元。"Z 世代"消费者对零食的需求从"饱腹"转向"悦己 / 社交 / 体验"，垂直化、个性化、内容化成为新趋势。

**技术背景**：前后端分离架构是当下主流电商系统的工程实践范式。Spring Boot 在企业级后端开发中成熟稳定；Vue 3 + Composition API 在中后台与商城前台均有完善生态。

**教学背景**：本项目是计算机专业本科毕业设计作品，要求完整呈现"需求分析 → 系统设计 → 编码实现 → 测试 → 部署"的全流程工程能力。

### 2.2 项目目标

| 维度 | 目标 |
|------|------|
| 功能目标 | 完成可演示、可使用、可部署的垂直零食电商系统 |
| 技术目标 | 掌握 Spring Boot + Vue 全栈开发流程 |
| 差异化目标 | 实现**个性化推荐算法**与**数据可视化大屏**两大亮点功能 |
| 学业目标 | 通过毕业答辩，论文查重合规 |

### 2.3 产品愿景

> **"让零食购物像逛便利店一样简单"**
>
> 通过垂直化商品结构、场景化营销推荐、数据化运营决策，让用户在 3 分钟内完成零食选购决策，复购周期 ≤ 7 天。

### 2.4 业务边界说明

#### ✅ 系统做什么（In Scope）

1. 零食商品的展示、搜索、筛选、收藏、下单、支付流程
2. 用户账户体系、会员体系、积分体系
3. 后台对商品、订单、用户、营销的运营管理
4. 基于用户行为的个性化推荐
5. 销售与运营数据的可视化分析
6. 演示级数据初始化与运行支持

#### ❌ 系统不做什么（Out of Scope）

1. **不接入真实支付通道**（仅使用沙箱 / 模拟支付 / 虚拟钱包）
2. **不接入真实物流 API**（物流状态以管理员手动流转模拟）
3. **不做社交分享 / 内容 UGC**（评价仅限文本，无图片上传）
4. **不做 B2B / 经销商体系**
5. **不做移动端 APP**（仅 PC Web 端，可选响应式适配移动浏览器）
6. **不做供应链 / 仓储 / 采购模块**
7. **不接入真实推荐算力**（推荐算法为本机离线计算，不使用第三方推荐服务）
8. **不做限时秒杀 / 高并发抢购**（V1.1 修订中已明确移除，避免引入并发编程复杂度）

### 2.5 目标用户画像

| 角色 | 占比预期 | 典型场景 | 核心诉求 |
|------|----------|----------|----------|
| 🟦 游客 | 60% | 浏览首页、查看商品 | 决定是否注册 |
| 🟩 普通用户 | 30% | 注册、下单购物 | 顺畅的购物流程 |
| 🟨 会员用户 | 8% | 复购、参与活动 | 优惠、积分、专属感 |
| 🟥 后台管理员 | 2% | 商品管理、订单处理、数据分析 | 高效运营工具 |

**用户画像 1：小白零食党（普通用户主体）**
- 年龄：18-28 岁
- 特征：决策快、冲动消费、对价格敏感、喜欢凑单满减
- 痛点：超市零食区找不到想要的、网购推荐不准

**用户画像 2：囤货达人（会员用户主体）**
- 年龄：25-35 岁、月消费 ≥ 500 元
- 特征：习惯固定品牌、关注新品、愿意为高质量付费
- 痛点：想买新品尝鲜但怕踩雷

格式：`F-[子系统]-[序号]`

- **F-U**：前台用户端（User）

### 4.3 推荐模块（核心差异化 ② ⭐⭐⭐）

> **为什么做这个**：在所有 Spring Boot + Vue 商城毕设中，**90% 没有推荐系统**。这是从"CRUD 项目"升级为"智能化产品"的分水岭。推荐算法同时体现了：
> - **数据采集能力**（埋点 / 行为日志）
> - **数据处理能力**（离线计算 / 缓存）
> - **业务结合能力**（冷启动 / 多场景召回）
>
> 这是答辩时**最值得展开讲**的模块。

#### 4.3.1 功能详细设计

| 功能编号 | 功能名称 | 功能描述 | 优先级 |
|---------|----------|----------|--------|
| F-R-001 | **用户行为采集** | 埋点采集 4 类行为：浏览（PV）、加购、下单、收藏 | **P0 ⭐** |
| F-R-002 | **数据存储设计** | 行为日志写入 `user_behavior_log` 表，异步落库 | **P0 ⭐** |

#### 4.3.2 推荐流程（数据流）

```
                       ┌──────────────────────────────┐
                       │  用户行为采集 (前端埋点)       │
                       │  - 浏览 / 加购 / 收藏 / 下单  │
                       └─────────────┬────────────────┘
                                     │ HTTP
                                     ▼
                       ┌──────────────────────────────┐
                       │  行为日志落库                 │
                       │  user_behavior_log 表         │
                       └─────────────┬────────────────┘
                                     │
                                     ▼
                  ┌──────────────────────────────────┐
                  │  离线计算任务（每日凌晨 3 点）    │
                  │  Item-CF 算法                    │
                  │  计算物品相似度矩阵              │
                  └─────────────┬────────────────────┘
                                │
                                ▼
                  ┌──────────────────────────────────┐
                  │  Redis 缓存推荐结果              │
                  │  Key: rec:user:{userId}         │
                  │  Key: rec:item:{itemId}         │
                  │  TTL = 24h                       │
                  └─────────────┬────────────────────┘
                                │
                                ▼
   用户访问首页/详情页  ◀──────┬──────────────────────────┐
                              │   实时推荐接口             │
                              │   /api/recommend/...      │
                              └───────────────────────────┘
```

#### 4.3.3 Item-CF 核心算法简述

**输入**：用户行为日志（user_id, item_id, behavior_type, timestamp）

**步骤**：
1. **构建用户-物品矩阵**：用户 u 对物品 i 的隐式反馈权重 w（浏览=1，加购=3，收藏=4，下单=5）
2. **物品共现矩阵**：物品 i 与物品 j 同时被同一用户行为的次数
3. **相似度计算**：采用余弦相似度（Cosine Similarity）：

   $$ sim(i, j) = \frac{|U_i \cap U_j|}{\sqrt{|U_i| \cdot |U_j|}} $$

4. **Top-N 召回**：对目标物品取 Top-20 相似物品作为推荐结果
5. **用户推荐**：融合用户最近交互过的 N 个物品的相似物品集合，按分数排序

**冷启动**：
- 新用户（无行为）：直接返回"热门商品 TOP20"
- 新商品（无交互）：降权至冷启动池，等待首日数据

**为什么选 Item-CF 不选 User-CF**：
- 电商场景下用户量远大于商品量
- Item-CF 性能稳定，结果可解释（"买了 X 的人也买了 Y"）
- 计算量小，单机可完成

#### 4.3.4 推荐效果展示（答辩话术）

> "在本系统中，每个用户登录后看到的首页'为你推荐'位是基于他**过去 30 天的浏览、加购、收藏、下单行为**进行 Item-CF 算法计算得来。结果实时从 Redis 缓存读取。离线任务每日凌晨重新计算相似度矩阵，**保证推荐新鲜度与计算成本的平衡**。在答辩演示时，我会切换不同账号让评委看到推荐结果的差异。"

## 七、业务规则

### 7.1 订单状态流转规则

**状态枚举**：

| 状态码 | 中文名 | 说明 |
|--------|--------|------|
| PENDING_PAY | 待付款 | 已提交未支付 |
| PENDING_SHIP | 待发货 | 已支付待发货 |
| PENDING_RECEIVE | 待收货 | 已发货待确认收货 |
| COMPLETED | 已完成 | 已确认收货或超时自动完成 |
| AFTER_SALE | 售后中 | 已发起退款申请 |
| REFUNDED | 已退款 | 退款完成 |
| CANCELED | 已取消 | 用户取消或超时关闭 |

**状态机图**：

```
   ┌──────────┐
   │ 待付款   │
   └────┬─────┘
        │ (1)用户支付          │ (2)用户取消 / 超时未付
        ▼                      ▼
   ┌──────────┐           ┌──────────┐
   │ 待发货   │           │ 已取消   │
   └────┬─────┘           └──────────┘
        │ (3)管理员发货
        ▼
   ┌──────────┐           ┌──────────┐
   │ 待收货   │ ────────▶ │ 售后中   │
   └────┬─────┘  (5)申请  └────┬─────┘
        │       退款          │
        │ (4)确认收货         │ (6)管理员审核通过
        ▼                     ▼
   ┌──────────┐           ┌──────────┐
   │ 已完成   │           │ 已退款   │
   └──────────┘           └──────────┘
```

**流转规则说明**：
- (1) 用户支付 → PENDING_SHIP（自动）
- (2) 用户主动取消 / 超时 30 分钟 → CANCELED，库存自动回滚
- (3) 管理员标记发货 → PENDING_RECEIVE
- (4) 用户确认收货 → COMPLETED
- (5) PENDING_RECEIVE / COMPLETED 状态可发起退款 → AFTER_SALE
- (6) 管理员审核通过 → REFUNDED，库存回滚

### 7.2 退款规则

| 项 | 规则 |
|----|------|
| 退款时效 | 待发货状态可"取消订单"全额退款；待收货 / 已完成状态 7 天内可申请退款 |
| 退款方式 | 原路退回，本系统默认退回用户钱包 |
| 库存处理 | PENDING_SHIP 状态退款 → 回滚库存；PENDING_RECEIVE / COMPLETED 退款 → 不回滚 |
| 审核时效 | 演示环境下管理员手动审核，无 SLA |
| 拒绝退款 | 需填写拒绝原因 |

### 7.3 积分规则

| 场景 | 积分变化 |
|------|----------|
| 下单成功 | 实付金额 × 1（每消费 1 元获 1 积分） |
| 评价商品 | +5 积分 / 次 |
| 注册礼包 | +100 积分 |
| 订单取消 / 退款 | 积分回退 |
| 积分用途 | 兑换优惠券、参与积分活动 |

### 7.4 优惠券规则

| 维度 | 规则 |
|------|------|
| 类型 | 满减券、折扣券 |
| 有效期 | 固定时间段领取后 N 天有效 |
| 使用门槛 | 满 X 元可用 |
| 叠加规则 | 单笔订单仅可使用 1 张优惠券 |
| 库存 | 优惠券发行总量控制，先到先得 |
| 退款处理 | 订单退款时优惠券原额退回用户券包（若仍在有效期内） |

### 7.5 会员等级规则

| 等级 | 成长值阈值 | 权益 |
|------|-----------|------|
| V0 普通 | 0 - 499 | 基础下单 |
| V1 银卡 | 500 - 1999 | 每月领 1 张 9 折券 |
| V2 金卡 | 2000 - 4999 | 每月领 1 张 85 折券 + 双倍积分 |
| V3 钻石 | 5000+ | 每月领 1 张 8 折券 + 五倍积分 + 优先发货 |

成长值来源：
- 实付金额 1 元 = 1 成长值
- 退款时按比例扣减

> **会员优惠券发放机制（V1.1 新增）**：会员等级权益中的优惠券，由系统每月 1 日凌晨通过定时任务（`@Scheduled`）自动发放至用户券包，**无需用户手动领取**。发放规则为：每个等级对应一张固定折扣券，券有效期为当月自然月。此机制可避免开发积分兑换页面，降低工作量。

### 7.6 钱包充值规则（演示）

| 项 | 规则 |
|----|------|
| 充值入口 | 仅后台管理员手动为用户充值（演示场景） |
| 充值金额 | 整数，1 元起 |
| 退款退回 | 订单退款时退回用户钱包 |
| 提现 | 不支持 |
