## 5. 业务工作流详解

### 5.1 注册 / 登录（Captcha + JWT + BCrypt）

**验证码**：`CaptchaServiceImpl` 内存 `ConcurrentHashMap<id, Entry>` 存储 4 位字符（去除 0/O/1/I/L），5 分钟过期，**校验后立即消费**。演示环境直接返回明文 code，生产应只返 SVG。

**登录流程**（`UserServiceImpl.login:94-120`）：
```
verify captcha → selectOne by phone → BCrypt.matches → check status=0 黑名单
  → update lastLoginAt → JWT generate
```

**注册**：成功后**直接生成 token**（`AuthController.java:43-44`），前端无需再走一遍登录流程，避免再次需要验证码。

**JWT 7 天有效**（`JwtUtil.java:32`）；Claims 含 `sub=userId`、`type=user|admin`、`perms=List<String>`、`username`。密钥默认 32 字节+（短于 32 自动补 0）。

### 5.2 商品 / 分类 / SKU

- `IProductService.list` 支持 `categoryId + keyword + sort(default/price-asc/price-desc/sales-desc/rating-desc)`，单条 QueryWrapper + **内存聚合 SKU 库存回填 `t_product.inventory`**
- **SKU 同步规则**（`ProductServiceImpl.syncSkus`）：
  - 带 id 的 → 更新
  - 无 id 的 → 新增
  - 未在前端提交里的在库 SKU → 软下架（status=0），**不物理删除**（保留 `t_order_item.sku_id` FK 引用）

### 5.3 购物车 → 下单 → 支付（WALLET + ALIPAY）

```
[CartController.add] → upsert uk_user_sku
                       ↓
[OrderController.create] → OrderServiceImpl.create (PayMethod: WALLET|ALIPAY)
                       ↓
   算金额 + 校验库存 + 折扣券核验
   - 满减券：discount 字段 = 减金额
   - 折扣券：discount 字段 = 比率（0.8=八折），优惠 = 商品总额 × (1-比率)，上限 50 元
   ↓
   扣 SKU/product 库存 (selectById + setStock；读改写，未用乐观锁)
   ↓
   genOrderNo = "ORD-yyyyMMdd-HHmmssSSS-xxxx" (5 次重试防 uk 冲突)
   ↓
   insert order
   - WALLET: 直接扣钱包 + 加积分/成长值 (status=PENDING_SHIP)
   - ALIPAY: 保持 status=PENDING_PAY (后续由主动 query 或 notify 流转)
   ↓
   insert order_items (snapshot name/image/spec/price)
   ↓
   delete cart items
   ↓
   consume user_coupon (status→已用, 终身一次不能复用)
   ↓
   TransactionSynchronizationManager.registerSynchronization(afterCommit)
       → OrderNotifyService.broadcastNewOrder (SSE 给后台)
```

**订单号冲突重试**（`OrderServiceImpl.java:169-186`）：
```java
for (int i = 0; i < maxRetry; i++) {
    order.setOrderNo(genOrderNo());
    try { orderMapper.insert(order); break; }
    catch (Exception ex) {
        if (ex.getMessage().contains("Duplicate") || ex.getMessage().contains("uk_order_no")) continue;
        throw ex;
    }
}
```

**支付确认两种路径共用同一幂等函数**：
- **WALLET**（`OrderServiceImpl.payByWallet`）：`UPDATE t_order SET status='PENDING_SHIP' WHERE id=? AND status='PENDING_PAY'`（`markPaidByWallet`），affected=1 才扣钱包 + 加积分
- **ALIPAY**：异步通知（`AlipayServiceImpl.handleOrderNotify`）和主动查询（`queryOrderPay`）都调 `orderService.confirmAlipayPaid`，后者再调 `tOrderMapper.markPaidByAlipay`

### 5.4 钱包（CAS 原子更新）

**核心 SQL**（`TWalletAccountMapper.java:23-29`）：
```sql
UPDATE t_wallet_account
SET balance = balance + #{delta}
WHERE user_id = #{userId}
  AND (#{minRequired} IS NULL OR balance + #{delta} >= #{minRequired})
```

**关键设计点**：
- **下限检查内置于 WHERE**，应用层无需 SELECT 即可确保余额不会变负
- `affected = 0` 一并涵盖"账户不存在"和"余额不足"两种情况，由应用层二次查询区分
- 用于内部手动入账（`recharge`，仅服务层/运维脚本）+ 网关充值（`rechargeByGateway` → `AlipayServiceImpl.confirmPaid`）+ 支付（`pay`）+ 退款（`refund`）

**重复入账防护**：所有走支付宝的接口通过 `confirmPaid` 在单事务内 `UPDATE t_wallet_recharge_order SET status='PAID' WHERE out_trade_no=? AND status='PENDING'`（`TWalletRechargeOrderMapper.java:18-23`），affected=1 才加余额。重复 query/notify 不会重复入账。

> `/api/wallet/recharge` 现在只创建支付宝充值单并返回 `payForm`，**不会直接加余额**；用户付款后由 `/api/wallet/recharge/query` 主动查询或 notify 异步通知触发 `confirmPaid` 入账，避免任意用户凭空造钱。订单支付仍支持 WALLET + 沙箱双通道。

### 5.5 优惠券（Claim / Consume）

**终身一次领取由两层保证**：
```
应用层 selectCount > 0 → 抛 BizException
       ↓ 漏过
SQL UNIQUE INDEX (user_id, coupon_id)
       ↓ 仍漏过
INSERT 抛 DuplicateKeyException → 捕获后转 BizException
```

即使在并发双击 + 应用层 TOCTOU 漏洞下，唯一索引也兜底。最关键的并发扣库存由 `UPDATE t_coupon SET remaining=remaining-1 WHERE remaining>0` CAS 处理（`CouponServiceImpl.java:122-129`）。

**核销** `consume`：校验 status=可用、当前用户、未过期（过期则同步刷 status=过期 后抛错）。

### 5.6 商品评价（Purchase + Dedup）

`ReviewController.submit`：先 `checkEligibility` 三道校验（登录 → 已购 → 防重），再 insert，最后 try-catch 回写 t_product.rating。

- **已购** 通过自定义 SQL `countPurchasedProduct` 走 order + order_item join，状态限定 `IN ('PENDING_RECEIVE', 'COMPLETED')`
- **防重**：应用层查 (userId, productId) 已评过则返回 `ALREADY_REVIEWED` + 已有 reviewId。**未在 DB 上加 UNIQUE 索引**（注释明确"避免 schema 加 unique index 的额外迁移"），仅靠应用层 select
- **数据卫生**：`fetchRatingStats` 一次拿 totalCount/positiveCount/avgRating

### 5.7 推荐系统（ItemCF + Redis + Cold-Start）

**写路径**：
- 每日凌晨 3:00 `RecommendTask.dailyRebuild` cron
- 管理后台 `/api/recommend/admin/refresh` 手动触发（`@PreAuthorize("hasAuthority('dashboard:view')")`）
- 应用启动时 `RecommendWarmupRunner` 预热
- 数据范围：近 30 天行为 + 通过 `BehaviorScopes.realBehaviorOnly()` 过滤 list/test/uat 曝光

**算法**：`ItemCFEngine` 三步
1. `buildUserItemMatrix` 权重合并（VIEW=1 / ADD_CART=3 / FAVORITE=4 / ORDER=5）
2. `computeItemSimilarity` 余弦相似度 + Top-20 小顶堆（避免全排序）
3. `generateUserRecommendations` 排除已交互 + 取 Top-20

**读路径 4 级 fallback**（`RecommendServiceImpl.personalRecommend:48-81`）：
```
cached = redis GET rec:user:{uid}
  ↳ hit → return trim(limit)
miss → computePersonalOnTheFly (拉近 30 天 behavior, 实时算, TTL 1h 短缓存)
        ↳ OK → write Redis → return
miss → recommendByRecentCategories (按用户最近 30 天浏览/加购的分类偏好 + 评分取 TOP, 排除已交互)
        ↳ OK → return
miss → coldStart (rating-desc 全站 TOP N)
```

> **关键卫生策略**：`BehaviorScopes.java` 注释明确说 "前端列表页 watch() 会批量上报 source=list 的 VIEW，把曝光当浏览埋库"——通过 `JSON_UNQUOTE(JSON_EXTRACT(extra, '$.source'))` 强制只采纳 `source=detail` 或旧版 NULL 记录。

### 5.8 行为埋点（Behavior Tracking）

- 接口：`POST /api/behavior/report`，**已配 permitAll**，游客也可以上报（userId=null）
- `BehaviorServiceImpl.report` 加 `@Async`，**不阻塞主请求**
- `/api/behavior/recent-views` 调试接口：当前用户最近的浏览商品（去重 productId，最多 50 条），SQL 中加 `JSON_EXTRACT(extra, '$.source') = 'detail'` 过滤

### 5.9 后台运营（Log + Role/Permission）

- 登录 → `AdminServiceImpl.login` 一次性加载该 admin 全部角色 code + 权限 code → 写入 JWT `perms` claim
- RBAC 模型：`t_admin — N:M — t_role — N:M — t_permission`，4 张关联/主表，**实际只有 role 字段 + permission code 两种都会进 JWT**
- 操作日志：`OperationLogServiceImpl.log(module, event)` 在 admin controller 写操作成功处手动调用，写入 `t_operation_log`（operator 自动取当前 admin username, IP 走 XFF/X-Real-IP/RemoteAddr）

## 6. 横切关注点

### 6.1 全局异常处理（`GlobalExceptionHandler`）

`@RestControllerAdvice` 集中处理 7 类异常：

| 异常 | 响应 |
|---|---|
| `BizException` | 自定义业务码 + msg |
| `MethodArgumentNotValidException` / `BindException` / `ConstraintViolationException` | 校验失败拼接 msg 转 1001 `BAD_REQUEST` |
| `UnauthorizedException` | 401 `UNAUTHORIZED` |
| `org.springframework.security.core.AuthenticationException` | 401 |
| `AccessDeniedException` | 403 |
| `Exception` 兜底 | 9999 `INTERNAL_ERROR` |

### 6.2 Spring Security（`SecurityConfig.java:37-87`）

全部基于 `requestMatchers().permitAll()` 白名单 + `hasAnyRole("SUPER_ADMIN","OPERATOR")` 后台保护 + `hasRole("USER")` 前台保护 + `anyRequest().authenticated()` 兜底。

**公开路径**：
- `/api/auth/login,register`、`/api/captcha, /api/captcha/**`
- `/api/admin/auth/login`
- `/api/behavior/report, /api/behavior/**`（游客埋点）
- `/api/product/list, detail/**, categories`、`/api/sku, /api/sku/**`
- `/api/coupon/available`、`/api/banner/list`、`/api/announcement/list`
- `/api/notify/stream`（SSE）
- `/api/wallet/recharge/notify`、`/api/order/alipay/notify`（支付宝回调，必公开）
- `/img/**`（本地商品图）

**`JwtAuthFilter`**：把 JWT claims 解析成 `UsernamePasswordAuthenticationToken`，principal=name, authorities=`ROLE_user/admin` + 各 perm code, details Map 存 userId/username/type。

**`JsonAuthHandlers`**：Auth/AccessDenied 异常转 `R{401/403}` JSON，**注意 HTTP status 故意返回 200**（`JsonAuthHandlers.java:41`），让前端 axios 走业务码分支而非 error 分支。

**CORS**：`allowedOriginPatterns=*`，`allowCredentials=false`，methods/headers 全开。

### 6.3 MyBatis-Plus 自定义 SQL（7 个 Mapper 方法）

| Mapper | 方法 | 用途 |
|---|---|---|
| `TOrderMapper` | `countPurchasedProduct` | 评价已购校验（JOIN order+order_item, status IN） |
| `TOrderMapper` | `markPaidByAlipay` | 订单状态 CAS PENDING_PAY→PENDING_SHIP |
| `TOrderMapper` | `markPaidByWallet` | 余额补付同上 |

| `TProductMapper` | `updateRating` | 评价后回写 rating |

### 6.4 SSE 通知（新订单推送）

`OrderNotifyService`（68 行）：
- `subscribe()` 返回 `new SseEmitter(0L)`（不超时），放入 `ConcurrentHashMap`，三种回调都 `remove`
- `broadcastNewOrder(TOrder)` 在事务提交后被 `OrderServiceImpl.afterCommit()` 调用，事件名 `NEW_ORDER`，payload 含 orderNo/totalPrice/payMethod
- `SseEmitter.send` 失败则剔除 emitter（断线检测）
- 接口在 `NotifyController`，`SecurityConfig` permitAll（注释强调"事件只含提示信息"）

### 6.5 异步（`@Async`）

- `BehaviorServiceImpl.report` 加 `@Async`（`BehaviorServiceImpl.java:25`）
- `MelodyShopApplication` 启动类 `@EnableAsync` 开启
- **未配置自定义 Executor**，默认走 `SimpleAsyncTaskExecutor`（生产应配 ThreadPoolTaskExecutor）

### 6.6 定时任务（`RecommendTask`）

- `dailyRebuild` 方法标 `@Scheduled(cron = "0 0 3 * * ?")`，每日 03:00
- `rebuildAll()` 是公开方法，也被 `RecommendWarmupRunner` 启动时调和管理员手动刷新入口共用

### 6.7 支付宝沙箱集成

- 配置集中在 `application.yml` `alipay:` 块（appId / gateway / privateKey / publicKey / charset / signType / format / returnUrl / notifyUrl + 订单专属 orderReturnUrl/orderNotifyUrl）
- `AlipayConfig` 用 `@ConfigurationProperties(prefix="alipay")` 加载，提供 `alipayClient()` 单例和 `alipayTransactionTemplate`（手写事务模板，仅包裹 confirmPaid）
- 主动查询/异步通知**共用** `confirmPaid`（充值）和 `orderService.confirmAlipayPaid`（订单）——二者都走 CAS + 已弃单幂等
- 验签 `AlipaySignature.rsaCheckV1` 失败直接 `return "fail"`，本地沙箱环境无公网入口使异步通知发不过来，靠主动 query 兜底

## 9. 核心设计模式

### 9.1 CAS 原子余额更新

`TWalletAccountMapper.atomicAddBalance` 是整个钱包系统的基石：

```sql
UPDATE t_wallet_account
SET balance = balance + #{delta}
WHERE user_id = #{userId}
  AND (#{minRequired} IS NULL OR balance + #{delta} >= #{minRequired})
```

- **下限检查内置于 WHERE**，应用层无需 SELECT 即可确保余额不会变负
- `affected = 0` 一并涵盖"账户不存在"和"余额不足"两种情况，由应用层二次查询区分
- 也用于 SKU 库存竞态防范思想（但 t_product_sku 实际用 `selectById + updateById` 读改写，仍有理论竞态窗口，详见第 10 节）

### 9.2 幂等订单支付确认

| 路径 | SQL |
|---|---|
| 订单 | `UPDATE t_order SET status='PENDING_SHIP' WHERE id=? AND status='PENDING_PAY'` |
| 充值 | `UPDATE t_wallet_recharge_order SET status='PAID' WHERE out_trade_no=? AND status='PENDING'` |

主动 query 与异步 notify 都走它，确保只生效一次。加积分的 `addPointsAndGrowth` 在两个 CAS 之后才执行，确保积分不会因重试乱发。

### 9.3 优惠券"终身一次"双保险

```
应用层 selectCount > 0 → 抛 BizException
       ↓ 漏过
SQL UNIQUE INDEX (user_id, coupon_id)
       ↓ 仍漏过
INSERT 抛 DuplicateKeyException → 捕获后转 BizException
```

即使在并发双击 + 应用层 TOCTOU 漏洞下，唯一索引也兜底。最关键的并发扣库存由 `UPDATE t_coupon SET remaining=remaining-1 WHERE remaining>0` CAS 处理。

### 9.4 ItemCF Cold-Start 分级兜底

`RecommendServiceImpl.personalRecommend` 4 级 fallback：
1. Redis 命中（KEY_USER_REC + uid）→ 返回
2. Redis miss → `computePersonalOnTheFly` 实时算（仅该用户，TTL 1h 短缓存）
3. ItemCF 数据稀疏 → `recommendByRecentCategories` 按用户最近 30 天浏览/加购的分类偏好 + 分类内 rating-desc
4. 完全无行为 → `coldStart`（全商品 rating-desc TOP N）

### 9.5 行为埋点公开路径白名单

`SecurityConfig.permitAll` 把 `/api/behavior/report, /api/behavior/**` 暴露给游客，但 `BehaviorServiceImpl.report` 接受 userId=null，使得未登录也能参与推荐训练，仅排除自身识别能力。

### 9.6 事务提交后广播 SSE

使用 `TransactionSynchronizationManager.registerSynchronization`（`OrderServiceImpl.java:220-225`）而不是 `@TransactionalEventListener(phase=AFTER_COMMIT)`——更轻量，不依赖 `ApplicationEventPublisher`。保证：事务回滚则不广播，避免虚假通知。

### 9.7 自动注册的拉新奖金

注册成功立即 `walletMapper.insert` + `pointLogMapper.insert`，确保新用户钱包 + 积分流水同时建立（`UserServiceImpl.java:74-87`），强一致。
